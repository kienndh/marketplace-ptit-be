# KỸ NĂNG KIỂM DUYỆT MÃ NGUỒN JAVA (MARKETPLACE JAVA CODE REVIEW SKILL)

Kỹ năng này định nghĩa quy trình kiểm duyệt (Code Review) gồm 8 bước bắt buộc áp dụng trước khi hoàn tất bất kỳ Pull Request hoặc Task nào trong dự án di trú `marketplace-ptit-be`.

---

## BƯỚC 1: KIỂM TOÁN RANH GIỚI WORKSPACE VÀ NHÁNH GIT (WORKSPACE & GIT SANITY)
- **Kiểm tra ranh giới repository**:
  - Đảm bảo **TUYỆT ĐỐI KHÔNG** có thay đổi nào trong `student-marketplace-be/` và `student-marketplace-fe/` (`git status` trong các repo này phải sạch 100%).
  - Tất cả thay đổi chỉ được nằm trong `marketplace-ptit-be/` (hoặc tài liệu quản trị chung tại root nếu có yêu cầu tường minh).
- **Kiểm tra nhánh**:
  - Xác nhận đang làm việc trên đúng nhánh quy định (mặc định là `main` cho giai đoạn bootstrap).
- **Kiểm tra file rác**:
  - Đảm bảo không commit `.class`, `.jar`, file tạm của IDE (`.idea/`, `.vscode/`), `.env`, file dump CSDL hoặc secrets.

---

## BƯỚC 2: BIÊN DỊCH VÀ XÂY DỰNG MAVEN (COMPILATION & MAVEN BUILD VERIFICATION)
- **Kiểm tra lệnh build**:
  - Chạy `./mvnw clean compile` hoặc `mvn test-compile`.
- **Tiêu chuẩn vượt qua**:
  - Quá trình biên dịch kết thúc với `BUILD SUCCESS`.
  - 0 lỗi biên dịch (Compilation Errors).
  - Không có cảnh báo ép kiểu nguy hiểm (Unchecked casts) hoặc xung đột thư viện phụ thuộc trong `pom.xml`.

---

## BƯỚC 3: ĐỐI SOÁT SCHEMA VÀ MIGRATION FLYWAY (SCHEMA & MIGRATION PARITY)
- **Đối soát với DB_v7.md**:
  - Mọi bảng mới, cột mới, chỉ mục (Index), khóa ngoại (Foreign Key), ràng buộc CHECK phải khớp chính xác với `student-marketplace-be/docs/DB_v7.md`.
- **Cú pháp PostgreSQL 15+ Native**:
  - Không chấp nhận cú pháp MySQL (`AUTO_INCREMENT`, `DATETIME`, `ON UPDATE CURRENT_TIMESTAMP`).
  - Phải dùng đúng cú pháp PostgreSQL: `BIGINT GENERATED BY DEFAULT AS IDENTITY`, `TIMESTAMP WITHOUT TIME ZONE`, `NOW()`, `TIMESTAMPTZ`, `UUID`.
- **Quy chuẩn Flyway**:
  - Tên file migration: `V<version>__<description>.sql`.
  - Tính lũy thừa và an toàn: Các migration phải kiểm tra an toàn (safe DDL), không làm gián đoạn CSDL đang chạy.
  - Phù hợp với cấu hình baseline nếu CSDL đã tồn tại bảng từ trước.

---

## BƯỚC 4: TÍNH CHUẨN XÁC CỦA ÁNH XẠ JPA / HIBERNATE (ENTITY & DOMAIN MAPPING FIDELITY)
- **Bảo toàn ddl-auto: validate**:
  - Cấu hình `spring.jpa.hibernate.ddl-auto` bắt buộc phải là `validate`.
  - Schema CSDL trong PostgreSQL thật và entity Java phải khớp nhau từng chi tiết để Hibernate validate thành công khi ứng dụng khởi động.
- **Ánh xạ kiểu dữ liệu đặc thù**:
  - **Khóa chính**: Ánh xạ đúng giữa `GenerationType.IDENTITY` và sequence/identity trong PostgreSQL.
  - **UUID**: Các trường như `public_id` trong `users` phải dùng kiểu `java.util.UUID`.
  - **PostgreSQL Custom ENUM**: Đối với các enum CSDL như `user_status` và `payment_status_t`, phải cấu hình mapping tương thích với PostgreSQL (không để Hibernate gửi VARCHAR gây lỗi ép kiểu trong câu truy vấn).
  - **JSON**: Các cột kiểu JSON như `social_links` phải dùng converter hoặc Hibernate JSON type thích hợp.

---

## BƯỚC 5: KIẾN TRÚC PHÂN TẦNG VÀ XỬ LÝ LỖI (LAYERED ARCHITECTURE & EXCEPTION CONTRACT)
- **Kiến trúc phân tầng**:
  - Controller -> Service -> Repository -> Entity.
  - Không viết logic nghiệp vụ trong Controller hoặc Repository.
  - Không gọi Repository trực tiếp từ Controller mà phải qua Service.
- **Quản lý Transaction**:
  - Các service method đọc dữ liệu phải có `@Transactional(readOnly = true)`.
  - Các service method ghi/sửa dữ liệu phải có `@Transactional`.
- **Không để lộ Entity**:
  - Controller tuyệt đối không trả về đối tượng `@Entity` ra API response. Bắt buộc phải chuyển đổi qua Response DTO / Record để tránh vòng lặp Jackson, LazyInitializationException và lộ dữ liệu nhạy cảm.
- **Xử lý ngoại lệ chuẩn tắc**:
  - Ném `ApiException` với HttpStatus phù hợp (400, 401, 403, 404, 409, 422).
  - Không để lộ stack trace hoặc thông tin CSDL nội bộ ra client. `ErrorHandler` format lỗi theo định dạng chuẩn.

---

## BƯỚC 6: TƯƠNG THÍCH HỢP ĐỒNG API VÀ DTO (API CONTRACT & DTO PARITY)
- **Đối soát với API_CONTRACT.md**:
  - Đường dẫn endpoint: `/api/v1/...` đúng chuẩn.
  - HTTP Method: `GET`, `POST`, `PUT`, `PATCH`, `DELETE`.
  - Request body & Response body: Tên thuộc tính (camelCase), định dạng ngày tháng (ISO-8601), và cấu trúc phân trang khớp với backend Python.

---

## BƯỚC 7: KIỂM THỬ THỰC CHẤT VỚI DATABASE THẬT (TEST VERIFICATION & INTEGRATION)
- **Chạy bài kiểm thử**:
  - Thực thi `./mvnw test`.
- **Nguyên tắc không dùng Mock gian lận**:
  - Với các nghiệp vụ có ràng buộc tính toàn vẹn dữ liệu (Unique partial index, Foreign Key RESTRICT/CASCADE, Pessimistic Locking trong đấu giá), bắt buộc phải có bài kiểm thử tích hợp chạy với CSDL PostgreSQL thật (`marketplace_java_dev`).
  - Không chấp nhận bài test chỉ dùng Mockito để giả lập repository thành công khi logic CSDL chưa được kiểm chứng.
